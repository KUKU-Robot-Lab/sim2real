# VLM 감독 계획 (칵테일 제조 자동 진행)

2026-11-16 사용자 승인. 담당 general_lab. VLM 감독 트랙의 정본 계획이다.

## 목표

실기에서 VLM(Cosmos-Reason2-8B + 감독기)이 정해진 순서의 정책을 실행하고, 노드 사이를 잇고, 실패하면 복구를 고른다. sim 은 배선을 확인하는 도구이고 VLM 정확도는 실기 사진으로 잰다(11.16 사용자). 접근은 뒤 단계에서 VLM 이 맡고 잡기부터는 rcg04 정책이 한다(11.10 사용자).

## 11.16 진단

기준선은 server GPU0 에서 구슬을 켠 oneshot 1 env 를 시드별로 돌린 `logs/vlm_sup/vlm_full_1116` 이다.

| 구분 | 문제 | 근거 |
|---|---|---|
| 판정 | 사진과 무관하게 성공이라 답한다 | 사진만 주는 판정 49건 중 47건이 성공. 참값 실패 4건(붓기 3, 놓기 1)을 모두 통과시켰다 |
| 판정 | 원인 가설(재생 시험 전) | 입력 12,580 토큰 중 스킬 카드 전체가 89 %, 사진은 7 %. 호출마다 바뀌는 글은 노드 이름 하나. 맨 끝 문장이 terminal 카드의 "세 컵이 홀더에 있는가" |
| 판정 | 근거 없는 중단 | 8개 시드 중 2개가 scene 에서 stop. 거의 같은 사진에 "홀더에 놓였다"와 "안 보인다"가 나온다 |
| 판정 | 사진에 없는 것을 묻는다 | 구슬은 6~7 px, 붓기 앞뒤 사진 차는 2.8/255 |
| 감독 루프 | 첫 READY 에서 판정을 부른다 | `supervisor.py:104` 의 `if last:` 가 빈 틀 dict 에도 참이다 |
| 감독 루프 | 놓기 뒤 경계 둘에 판정이 없다 | `cocktail_1c_e4000.yaml` 58·69행의 `home_r_after_blue`, `go_home_end` 가 `auto: true` 라 승인 없이 이어진다 |
| 계획 | VLM 계획 13회가 모두 형식에서 탈락 | 손 칸 규칙이 모호하고 왼손 셰이커 잡기가 빠진다. `--plan_order off` 라 순서에는 안 쓰인다 |
| sim 배선 | 복구를 sim 에서 시험하지 못한다 | 브리지가 rescan·reorder 를 못 받고 retry 는 복구 대기 때만 받는다 |
| 실기 연결 | 실물과 붙여 시험한 기록이 없다 | 러너 서비스는 next/run/stop/reset. 8B 서버는 server 127.0.0.1:8766. 실기 사진 평가 자료 0장 |
| 실기 연결 | 연속 실행에 VLM 이 끼어들 경계가 없다 | `episode_runner.py` 의 `run()` 은 READY 를 거치지 않고 끝까지 간다. `Approvals.take` 는 누가 쓴 승인인지 보지 않는다 |
| 체인 | 실기 칵테일 완주 기록이 없다 | sim 구슬 기준 e2e 4/16. 손실은 놓기 빼기와 붓기 양에서 난다 |

VLM 이 감독을 맡아도 체인 성공률이 저절로 오르지는 않는다. 놓기 빼기와 붓기 양은 정책 쪽 일이다.

## 방향

사진에는 보이는 것만 묻는다. 방금 끝난 노드의 스킬 카드 질문을 노드 인자로 채워 예/아니오로 묻고 전후 사진을 준다. 결정은 사진 답과 러너 신호(결과 코드, FP++, 촉각)를 합쳐 허용 행동(`failure_policy.allowed_actions`) 안에서 고른다. 애매하면 끝내지 않고 기존 `human` 행동으로 사람에게 넘긴다.

측정을 먼저 한다. 저장된 사진으로 호출당 몇 초짜리 시험대를 만들어 프롬프트를 바꿀 때마다 숫자로 본다. 에피소드 한 번은 약 30분이 걸려 확인 수단으로 쓰지 않는다. vLLM 이나 행동 트리 엔진은 들이지 않는다. 기존 추론 서버에 선택지 점수와 사진 여러 장 입력만 더한다.

## 단계

거짓 통과는 실패인데 넘기는 것이고 거짓 보류는 멀쩡한데 세우는 것이다. 기준은 실패 사례 수로 센다. 같은 시드·장면에서 나온 사진은 서로 독립이 아니어서 장면 수를 같이 적는다.

| 단계 | 하는 일 | 통과 기준 | 실행 위치 |
|---|---|---|---|
| 0 기준선·정리 | 기준선 표 확정(첫 READY 행 제외). 조직도·`MODULES.md` 등록. server 에 손으로 둔 추론 서버를 저장소로 옮김 | 기준선 표 한 장 | laptop, server 로그 |
| 1 판정 시험대 | 저장된 경계 사진과 러너 참값으로 (사진, 질문, 정답) 묶음을 만든다. 가설 시험으로 긴 현 프롬프트와 짧은 예/아니오에 맞는 사진, 다른 사진, 검은 사진을 넣어 답이 바뀌는지 본다. 실기 bag 사진 재고를 읽기 전용으로 센다 | 현 프롬프트의 오판이 재현되고, 프롬프트 문제인지 모델 한계인지가 갈린다 | server GPU0(VLM 사본 8767), sim 없음 |
| 2 판정·결정 재설계 | 방향대로 구현한다. 첫 READY 판정을 고치고, auto 로 이어진 노드와 lanes 노드는 뒤 경계에서 직전 노드까지 묻는다. 계획 지시문을 고친다. 결정은 규칙 표만 쓰는 안, 규칙 표에 사진 답을 더한 안, VLM 결정 안 셋을 같은 묶음으로 비교한다 | 시험대에서 쉬운 반례 거짓 통과 0, 정상 경계 60건 이상에서 거짓 보류 5 % 이하. 11.16 기록 재생에서 쓰러진 병을 잡고 seed1·2 장면을 통과한다 | laptop 편집, server 시험대 |
| 3 sim 배선 확인 | 어려운 반례 장면을 sim 에서 차려 촬영한다(기울어 앉은 컵, 홀더 테두리, 쓰러진 컵). 브리지에 retry·rescan 을 보강한다. 실패를 주입한다(잡기 실패, 놓은 뒤 쓰러짐, 접근 막힘) | 어려운 반례 30건 이상(장면 10종 이상)에서 놓침 0. 주입 장면마다 의도한 결정이 나온다 | server GPU0, 화면 띄움 |
| 4 실기 사진 평가 | 에피소드 bag 에서 경계 전후 사진을 뽑는다. 로봇 정지 상태에서 실패 장면을 차려 촬영한다(실패 사례의 주 공급원) | 실기 사진의 실패 30건 이상에서 놓침 0, 거짓 보류 5 % 이하. 못 미치면 실기 사진으로 LoRA | 5090·4090(읽기), server |
| 5 실기 연결(기록만) | 실기 PC 에서 server 8B 까지 경로와 지연을 잰다(서버 재시작 없이 터널). fake 도메인에서 ROS 통합 시험을 한다. 사람이 승인하는 실기 실행 옆에서 판정만 기록한다. 승인 파일에 감독기 줄이 0줄인지 점검한다 | 실패 30건 이상(차린 장면 포함)에서 놓침 0, 정상 경계 50개 이상에서 거짓 보류 5 % 이하, 경계당 5초 이내 | 실기 PC + server |
| 6 실기 자동 진행 | 새 러너 위에서 VLM 제안과 사람 확인으로 시작해 에피소드 1회 승인 안의 진행으로 올린다. 새 러너는 아래 "새 러너" 절대로 미리 설계하고 sim, fake 에서 먼저 돌린다 | 놓침률, 거짓 보류율, 경계당 시간. 실기 e2e 70 %(10.29 목표)는 정책 트랙 수치라 같이 보고만 한다 | 실기, 매번 허락 |
| 7 VLM 접근·순서 | 계획기가 낸 접근 후보를 사진에 번호 화살표로 그려 VLM 이 고른다(놓기 경로 판정 코드 재사용). 순서는 전제 조건이 맞는 다음 노드 후보 중에서 고른다. 끝 자세는 rcg04 시작 분포에 맞춘다 | sim, fake, 실기 순으로 같은 기준 | 5~6단계와 병행 |

1단계에서 짧은 질문으로도 쉬운 장면(컵이 홀더 안에 있는지 손 안에 있는지)을 못 가르면 모델 한계로 보고 2단계를 멈춘다. 그때는 손·홀더 영역 확대 입력, 2B, 다른 VLM 을 같은 시험대에서 먼저 본다.

## 새 러너

기존 러너는 VLM 이 진행을 맡을 구조가 아니다. 연속 실행은 노드 사이에서 멈추지 않는다. 구분 실행에서 VLM 이 next 승인 줄을 쓰면 사람 허락을 VLM 이 대신하게 되고, 러너는 누가 쓴 승인인지 구분하지 못한다. 그래서 VLM 에 맞는 러너를 새로 만든다(11.16 사용자). 기존 러너는 VLM 없이 돌리는 운용을 위해 그대로 둔다.

새 러너가 갖출 것은 다섯 가지다. 모든 노드 뒤(auto, lanes 포함)에 경계를 두고 전후 사진을 직접 확보한다. VLM 은 판정만 내고 사람 승인 줄을 쓰지 못한다. 답이 없거나 늦으면 정해진 기본 동작으로 간다. 다음 노드는 전제 조건이 맞는 후보 중에서 고르며 고정 순서가 기본 순위다. sim 과 실기가 같은 접점을 쓴다.

설계안은 `RUNNER_DESIGN.md` 로 따로 쓰고 사용자 승인 뒤 구현한다. 실기 허락 규칙의 문구, 물체를 든 채 사람에게 넘길 때의 시간 상한과 상한 뒤 동작, `deploy/policy_control` 에서 바뀌는 곳은 설계안에서 사용자와 s2r:deploy 가 정한다. 2~3단계의 sim 작업은 새 러너의 접점을 기준으로 한다.

## 하지 않는 일

sim 다시드 대량 실행, VLM 자유 계획으로 순서 제어, 붓기 양의 사진 판정은 하지 않는다. 붓기를 러너 신호(기울인 시간, 손목 각, 촉각)로 다룰 수 있는지는 tilt 쪽과 따로 본다.

## 위험

8B 가 고친 뒤에도 실기 사진에서 기준에 못 미칠 수 있다. 공개 벤치(FailBench)에서도 최고 균형 정확도가 0.77 이다. 보이는 것만 묻기, 러너 신호와 결합하기, 사람에게 넘기기, 실기 사진 LoRA 로 대비한다.

실기 체인이 아직 완주하지 못해 6단계 수치는 정책 쪽 일정에 묶인다. 5단계의 기록 전용 방식은 그와 무관하게 진행할 수 있다.

server 8B 를 랜으로 쓰면 실기 PC 와 server 사이 통신이 끊길 때 판정이 늦어진다. 시간 안에 답이 없으면 사람에게 넘긴다.

## 재사용

스킬 카드의 질문·시작 조건, 실패 정책 표, 놓기 경로 화살표, 판정 기록 폴더, 테스트 149개, 실기 러너의 서비스·상태 토픽·승인 파일을 그대로 쓴다. 외부에서는 Cosmos 프롬프트 가이드(사진을 글보다 앞에, 질문형), Guardian·Sentinel 의 전후 사진 입력, KnowNo 의 "불확실하면 묻기", RoboFAC 의 LoRA 절차를 참고한다.
